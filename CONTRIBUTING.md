# Contributing to ConcurrencyBugBench

Thank you for taking the time to contribute! Below are the guidelines to help keep the project consistent and high‑quality.

## Getting Started
1. **Fork the repository** and clone your fork.
2. **Create a new branch** for your work:
   ```bash
   git checkout -b feature/your-feature-name
   ```
3. **Install the development dependencies**:
   ```bash
   python -m pip install -r requirements.txt -r requirements-dev.txt
   ```
4. **Run the test suite** to ensure everything passes before you start:
   ```bash
   pytest
   ```

## Code Style
- Use **Black** for formatting (`black .`).
- Use **isort** to sort imports (`isort .`).
- Lint with **ruff** (`ruff check .`).
- Type‑check with **mypy** (`mypy .`).
- All files must pass `pre‑commit` checks (see the *Pre‑commit* section).

## Commit Messages
- Follow the **Conventional Commits** style:
  - `feat:` for new features
  - `fix:` for bug fixes
  - `docs:` for documentation changes
  - `test:` for adding or updating tests
  - `refactor:` for code changes that neither fix a bug nor add a feature

## Pull Request Process
1. **Push** your branch to your fork.
2. Open a PR against the `main` branch.
3. Ensure the CI pipeline passes (tests, lint, type‑check).
4. Fill out the PR template, describing the changes and any relevant issue numbers.
5. Request review from at least one maintainer.

## Testing
- **Unit tests** live under the `tests/` directory.
- **Integration tests** may be added under `tests/integration/`.
- Aim for **90 %+ coverage**. Coverage reports are generated by the CI workflow.

## Pre‑commit Hooks
We ship a pre‑commit configuration. After cloning, run:
```bash
pre-commit install
```
This will automatically format, lint, and check files on each commit.
